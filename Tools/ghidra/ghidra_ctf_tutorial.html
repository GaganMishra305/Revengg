🚀 First Launch — Project Setup
Ghidra is Project-Based
Unlike r2/GDB, Ghidra requires you to create a Project first, then import binaries into it. Projects store your analysis, notes, renamed symbols, and comments persistently — extremely valuable for CTFs with multiple related binaries.
Create a new project
File→ New Project→ Non-Shared Project→ Choose directory & name→ Finish
Import a binary
File→ Import File→ Select binary→ OK (auto-detects format)
Auto-detection
Ghidra auto-detects ELF, PE, Mach-O, raw binary, firmware, and more. For raw firmware: choose "Raw Binary" and set the correct architecture manually.
Open in CodeBrowser (the main analysis window)
Double-click binary→ Analyze? → Yes→ Analyze (accept defaults)
💻 Headless Mode (No GUI — great for scripting)
shell
# analyzeHeadless is inside support/ directory ./support/analyzeHeadless /tmp/myproject MyProject \ -import ./binary \ -postScript ExportFunctions.py \ -scriptPath ./scripts # One-liner to analyze and run a script: ./support/analyzeHeadless /tmp/proj Proj -import ./bin -postScript Decompile.java # Analyze without running a script (just pre-analyze): ./support/analyzeHeadless /tmp/proj Proj -import ./bin -analysisTimeoutPerFile 60

Lesson 04 · Analysis
The Decompiler Window
Ghidra's decompiler is its crown jewel. It converts assembly back into readable C pseudocode — not perfect, but close enough to understand logic in minutes rather than hours.
C pseudocodevariable typesright-click actionssync with Listing
📖 Reading Decompiler Output
example decompiler output — annotated
/* Initial output — before renaming/retyping */ undefined8 FUN_00401156(void) { int iVar1; char local_48 [64]; // stack buffer — auto-sized long local_10; // suspicious: probably the canary local_10 = *(long *)(in_FS_OFFSET + 0x28); // canary read from TLS puts("Enter password: "); fgets(local_48, 0x40, stdin); iVar1 = strcmp(local_48, "s3cr3t_k3y\n"); // ← the check! if (iVar1 == 0) { FUN_00401100(); // ← probably win() } if (local_10 != *(long *)(in_FS_OFFSET + 0x28)) { __stack_chk_fail(); // canary check } return 0; }
💡 What to Look For Immediately
1. strcmp / memcmp — password comparison. Check the second argument for the expected string.
2. FUN_XXXXXXXX calls — unknown functions. Double-click to navigate, check if it's a "win" function.
3. Buffer sizes — char local_48[64] with fgets(local_48, 0x40, ...) is safe. With gets: overflow possible.
4. in_FS_OFFSET+0x28 — that's the stack canary. Don't be confused by it.

The Listing is Ghidra's disassembler view. It shows assembly with labels, xrefs, and data annotations. The Decompiler is higher-level, but the Listing is truth — use both together.

📋 Reading the Listing
Ghidra Listing — annotated
; *** FUNCTION *** undefined8 FUN_00401156(void) XREF[1]: main:00401200(c) FUN_00401156 PUSH RBP 00401157 MOV RBP,RSP 0040115a SUB RSP,0x50 0040115e MOV RAX,qword ptr FS:[0x28] ; canary 00401167 MOV qword ptr [RBP + local_10],RAX 0040116b LEA RDI,[s_Enter_pass_00402010] ; = "Enter password: " 00401172 CALL <EXTERNAL>::puts 00401177 LEA RDI,[RBP + local_48] ; buf 0040117b MOV ESI,0x40 00401180 MOV RDX,qword ptr [stdin] 00401187 CALL <EXTERNAL>::fgets 0040118c LEA RSI,[s_s3cr3t_k3y_00402020] ; = "s3cr3t_k3y\n" 00401193 LEA RDI,[RBP + local_48] ; user input 00401197 CALL <EXTERNAL>::strcmp
Listing vs Decompiler
The Listing is precise — exactly what the CPU executes. The Decompiler is approximate — a reconstruction. When the decompiler looks wrong, switch to Listing to see what's really happening. They're always synchronized — click in one, the other jumps to the same location.

Renaming & Retyping
The most important reversing workflow. As you understand code, you rename variables and functions to reflect reality. Ghidra immediately updates the decompiler output — a feedback loop that dramatically accelerates understanding.

✏ Renaming — The Most Used Action
how to rename in Ghidra
# In Decompiler or Listing: # Click on any variable / function name → press L # Type new name → Enter # Variable rename example: # BEFORE: int iVar1 = strcmp(local_48, param_1); # After pressing L on "iVar1" and typing "cmp_result": int cmp_result = strcmp(local_48, param_1); # Function rename — click function name → L: # FUN_00401100 → win_function # Updates everywhere it's called! # In Symbol Tree: right-click → Rename # Shortcut: N key also works on functions in Symbol Tree
🔧 Retyping Variables
fixing wrong types improves decompiler output
# Click variable → press T → type the correct type → Enter # Ghidra immediately re-decompiles with the new type # Examples: # undefined8 → void* or char* # int → bool or char or uint8_t # long → size_t or uintptr_t # BEFORE: undefined8 param_1 // Ghidra doesn't know the type # AFTER pressing T → typing "char *": char *user_input // Now shows pointer arithmetic correctly
🖊 Editing Function Signatures
Ghidra — fix arg count / types

⚡ The String → Function XRef Trick
Key CTF Technique
See an interesting string in Defined Strings (like "Correct!", "Nope", "/bin/sh", "flag{")? Right-click it → References → navigate directly to the function that uses it. Skip reading the whole binary — jump straight to the interesting logic.
step-by-step
1. Window → Defined Strings 2. Find "Correct!" or "/bin/sh" or "flag{" 3. Right-click → References → Show References to Address 4. Double-click the reference → jumps to the exact call site 5. Read the surrounding code in Decompiler → understand the check

Lesson 10 · Reversing
Patching Bytes
Ghidra can patch the binary on disk — change bytes, NOP instructions, replace jumps. Combined with its decompiler, this is a powerful way to verify your understanding and create modified binaries.
Patch InstructionNOPExport ProgramAssemble
✏ Patching Instructions
Ghidra — in Listing view
# Method 1: Patch Instruction (most powerful) # Right-click instruction in Listing → Patch Instruction # Type new assembly → Enter # Ghidra assembles it and writes the bytes # Method 2: Patch Bytes Right-click → Patch Bytes # Type raw hex bytes to write at that address # e.g. "90 90 90 90 90" to write 5 NOPs # Common patches: # JNE (75 XX) → JMP (EB XX) — force jump always # JE (74 XX) → NOP NOP — don't jump at all # CALL target → NOP x5 — skip function call
💾 Exporting the Patched Binary
Ghidra — critical step, patches don't auto-save to disk
# Patches are stored in the Ghidra project, NOT the original file # To get an actual runnable patched binary: File → Export Program # Choose format: "Original File" — exports the binary with your patches applied # Choose output path → OK # Now run the exported file to test your patch # After export: chmod +x ./patched_binary ./patched_binary
Important
Always export to a copy, never the original. Ghidra modifications are non-destructive to the imported file — they're in the project database. You must explicitly export to apply to disk.
⚡ Practical Patch Examples
common CTF patches
# 1. Skip a check entirely (NOP the conditional jump) # Find JNE/JE in Listing → Right-click → Patch Instruction → type "NOP" # May need to NOP 2-6 bytes depending on instruction size # 2. Force a jump (change JNE to JMP) # JNE 0x401180 → Patch Instruction → "JMP 0x401180" # 3. Force function return 0 or 1 # At function start → Patch Instruction → "XOR EAX,EAX" then "RET" # Or: "MOV EAX,1" then "RET" # 4. Skip anti-debug (ptrace check) # Find ptrace call → NOP the whole call + cmp/jne after it

Challenge 10: Patch to Win
15 min
▼
Compile: int auth(){return 0;} int main(){if(auth())puts("access granted");else puts("denied");}

Three methods — try all:

Method A — Patch the branch:
1. Find the JE/JZ in main (after testing auth()'s return)
2. Right-click → Patch Instruction → change to JMP to the "win" path
3. Export → run → see "access granted"

Method B — Patch auth() to return 1:
